# Deployment guide

How to deploy AccountManager to your own Cloudflare account (Workers, D1, and Access) so that only invited people can open it.

- Dashboard labels are as they appeared in English as of November 2026. The Cloudflare dashboard layout may change; if you can't find something, search for it by name.
- Your account subdomain, Access team name, AUD, and email addresses are environment-specific values. Do not write them in the repository.

---

## 1. Overview

| Component | What it does |
| --- | --- |
| Worker `account-manager-demo` | A single Worker serves both the UI (`dist/client`) and `/api/*`. It is published at `account-manager-demo.<account-subdomain>.workers.dev` |
| D1 `account-manager-demo` | Stores the encrypted data. Its ID goes in `wrangler.jsonc` (the ID alone does not give access to its contents) |
| Access | Sits in front of the workers.dev URL. Only people allowed by the policy can log in, using a one-time code sent by email |
| Worker secrets | The four listed below. Do not put them in `wrangler.jsonc` or anywhere in the repository |

### 1.1 Secrets

| Name | What it is | If it is lost |
| --- | --- | --- |
| `USER_ID_PEPPER` | Key used to derive user IDs from email addresses (32 random bytes) | It becomes impossible to tell whose data is whose. **Always keep a copy** |
| `AUTH_PEPPER` | Key used to check the verifier (32 random bytes) | Nobody can open the app any more (not even with the recovery key). **Always keep a copy** |
| `ACCESS_TEAM_DOMAIN` | Host name of your Access team (`<team-name>.cloudflareaccess.com`, without `https://`) | Look it up under Cloudflare One → Settings → Team domain and set it again |
| `ACCESS_AUD` | AUD of the Access application | Look it up under "AUD" on the Worker's Domains & Routes page and set it again |

- The two peppers cannot be read back once registered with Cloudflare. Keep a copy somewhere such as a password manager. Replacing them makes all existing data unusable.
- Use different values from the ones in your local development `.dev.vars`.
- The JWKS (Access public keys) is not registered. The Worker fetches it from `https://<ACCESS_TEAM_DOMAIN>/cdn-cgi/access/certs` (`worker/access.ts`).
- To check the registered names: `npx wrangler secret list` (values are not shown).

## 2. Running locally

```sh
npm ci
cp .dev.vars.example .dev.vars   # fill in the values (generate the peppers with e.g. openssl rand -base64 32)
npm run db:migrate:local
npm run dev
```

- With `ENVIRONMENT=development` and `DEV_ACCESS_EMAIL` in `.dev.vars`, the app runs locally as that user instead of going through Access. This bypass works only when the host is `localhost` or `127.0.0.1`.
- Sample data: `node scripts/seed-sample.mjs <dev-server-address>` (usage is described, in Japanese, at the top of the script).
- Run all checks at once: `npm run verify` (formatting, oxlint, type check, unit tests, build).

## 3. First deployment

Prerequisite: you are logged in (check with `npx wrangler whoami`).

### 3.1 Create the D1 database

```sh
npx wrangler d1 create account-manager-demo
```

Put the `database_id` from the output into `d1_databases` in `wrangler.jsonc`. Deployment uses `dist/account_manager_demo/wrangler.json`, which is generated by the build, so rebuild after changing the ID (`npm run verify` includes the build).

### 3.2 Create the tables in D1

```sh
npx wrangler d1 migrations apply account-manager-demo --remote
```

### 3.3 Register the two peppers

Do this once per key. The values appear in the output, so do it where your screen is not being recorded.

```sh
openssl rand -base64 32                  # keep a copy of the value
npx wrangler secret put USER_ID_PEPPER   # paste the saved value when prompted

openssl rand -base64 32
npx wrangler secret put AUTH_PEPPER
```

If the Worker does not exist yet, you will be asked whether to create it. Answering "yes" creates an empty Worker (it is overwritten by the deployment, and the secrets remain).

### 3.4 Deploy

```sh
npm run verify                # confirm the exit code is 0
npx wrangler deploy --dry-run # check what will be uploaded (.dev.vars is not uploaded)
npx wrangler deploy
```

- `wrangler.jsonc` sets `preview_urls: false` (no per-version preview URLs), because anyone could open them if you forgot to put Access in front of them.
- Between deploying and enabling Access, anyone can see the empty shell of the UI. While `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` are not set, every `/api/*` request is rejected with 401, so no data can be read.

### 3.5 Put Access in front of workers.dev

1. Open **Workers & Pages → account-manager-demo → Settings → Domains & Routes**.
2. In the Worker URL section, the Production row shows "Anyone with this URL can visit." Press **Enable Access** next to it.
3. When it changes to "An Access policy applies to this URL.", press **Manage** next to it (the **Edit Worker access** page opens).
4. Set the following:
   - **Scope**: **All traffic** (not Previews only).
   - **Authentication policy**: keep only the policy created for this app (see 3.6). Remove the automatically added "Cloudflare account members" with the × (this only removes it from this app; the policy itself is not deleted). Otherwise, anyone you later add as a member of your Cloudflare account will also be able to open the app.
   - **Session duration**: **24 hours**.
5. Press **Save changes**. **Do not press the red "Remove Worker-specific Access"** (it removes Access, and anyone will be able to open the app).
6. Note down the **AUD** value at the bottom right of the original page.

### 3.6 A policy for this app

- Create a policy just for this app. **Do not reuse a policy used by other apps.** Policies can be shared across apps, so editing one also changes who can get into the other apps and how long their logins last.
- Action: **Allow**; Include: **Emails**, with the email addresses of the people who will use the app.

### 3.7 Login method (One-time PIN)

- Check that **One-time PIN** is listed under **Cloudflare One → Integrations → Identity providers**. If it is not, add it with **Add new identity provider** (Zero Trust organizations created after 2026-06-18 do not get One-time PIN automatically).
- Access enabled from a Worker has no setting for choosing the login method. Whatever is in Identity providers is used.
- A code can be used only once and expires in 10 minutes. If an email security scanner opens the link first, you may see a message that the code has already been used. In that case, press **Request new code**.

### 3.8 Register the Access values

```sh
npx wrangler secret put ACCESS_TEAM_DOMAIN   # <team-name>.cloudflareaccess.com (without https://)
npx wrangler secret put ACCESS_AUD           # the AUD noted in step 6 of 3.5
npx wrangler secret list                     # check that all four names are present
```

Registered secrets take effect immediately, without redeploying.

### 3.9 Check

| Check | Expected result |
| --- | --- |
| Open the UI (`/`) without logging in | Redirected with 302 to the login page at `<team-name>.cloudflareaccess.com` |
| Open `/api/health` or `/api/me` without logging in | Also 302 |
| Log in, in a private window, as a person included in the policy | The first-time setup screen (「はじめての準備」) appears first |

---

## 4. Adding and removing users

- To add: add the email address under **Emails** in the Include of this app's policy (3.6) and save. The new user logs in the same way as in 3.9 and does the first-time setup themselves.
- To remove: delete the email address from the same policy and save. Their data is kept; if the address is added back, they can carry on where they left off with the same email address.
- Zero Trust Free has 50 seats. Each person who logs in uses one seat.

---

## 5. Redeploying

```sh
npm run verify
npx wrangler deploy --dry-run
npx wrangler deploy
```

- If you changed the tables (added to `migrations/`), run `npx wrangler d1 migrations apply account-manager-demo --remote` **before** deploying (in the reverse order, the new Worker fails when it reads columns that don't exist yet).
- Secrets and Access settings are kept across redeployments.
- After deploying, run the checks in 3.9 again.
